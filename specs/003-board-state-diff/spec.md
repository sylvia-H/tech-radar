# Feature Specification: 榜單狀態快照與變化偵測（Board State & Diff）

**Feature Branch**: `003-board-state-diff`

**Created**: 2026-07-15

**Status**: Draft

**Input**: User description: "F3 榜單狀態快照與變化偵測（003-board-state-diff）。把 F2 產出的兩領域當前榜單（AI / 前後端，各 top 15 追蹤深度）合成單一「跨領域綜合 top 10」推播榜（保底每領域至少 2 席、沿用 F2 統一尺「估算本週增星」），與上次推播的榜單快照比對，產出「新進 / 竄升 / 下降」三類變化；掉出 top 10 當次靜默、留榜但變化未達門檻亦靜默。榜單每三天推一次，節奏由狀態中的 `lastBoardPushAt` 計時（非 cron）。狀態為單一權威來源，且必須在推播成功後才寫回。本 Feature 不含 Discord 組版與推播（F7）、不含簡介生成（F5）、不含新聞（F4/F6）。驗收：連跑兩次，第二次只產出差異；未滿三日時榜單段整段跳過。"

## User Scenarios & Testing *(mandatory)*

本功能的「使用者」即專案擁有者（自用）。F2 已能產出一份可觀測的**當前榜單**（兩領域各 top 15），但每次執行看到的都是「整份榜」——擁有者其實只想知道「**跟上次比，有什麼不一樣**」。本 Feature 把「當前榜單」升級為「**跨執行的變化**」：挑出跨領域綜合 top 10、與上次推播的快照比對、只吐出真正變化的項目，並用狀態中的時間戳把節奏控制在每七天一次。

本階段**只產出變化結果與節奏判定供觀測（log 可印出），不組 Discord 版面、不推播、不生成簡介**——那些屬 F5 / F7。

### User Story 1 - 只看見「跟上次比的變化」（Priority: P1）

擁有者執行任務後，不再看到重述整份榜單，而是看到一份**變化清單**：哪些 repo 新進了跨領域綜合 top 10、哪些名次竄升、哪些名次下降。已經穩定留在榜上、名次沒有實質移動的 repo 完全不出現；掉出 top 10 的 repo 也不出現（當次靜默）。第一次執行時因為沒有「上次」可比，整份綜合 top 10 全數視為新進。

**Why this priority**: 這是憲章原則 III「只推變化、避免通知疲勞」在榜單側的具體實現，也是本專案「每日晨報」相對於「又一個資訊流」的核心差異點。沒有它，F7 就只能重述整份榜單，專案存在意義即消失。它本身即構成可展示的最小可用產品：擁有者能看到「這週榜上真正動了什麼」。

**Independent Test**: 以兩份「上次快照 / 本次榜單」的樣本資料執行變化偵測，檢視輸出是否只含新進／竄升／下降三類、且穩定留榜與掉出者確實不在其中；不依賴 Discord、LLM 或真實網路即可完整驗證。

**Acceptance Scenarios**:

1. **Given** 尚無任何上次快照（冷啟動），**When** 執行變化偵測，**Then** 跨領域綜合 top 10 的 10 筆全數列為「新進」，且無任何「竄升」或「下降」項目。
2. **Given** 上次快照存在且本次某 repo 不在上次快照中，**When** 執行變化偵測，**Then** 該 repo 列為「新進」。
3. **Given** 某 repo 同時存在於上次快照與本次榜單、且綜合名次前進至少 1 名（如 `#5 → #4`），**When** 執行變化偵測，**Then** 該 repo 列為「竄升」，並帶有上次名次與本次名次。
4. **Given** 某 repo 同時存在於上次快照與本次榜單、且綜合名次後退至少 1 名（如 `#4 → #5`），**When** 執行變化偵測，**Then** 該 repo 列為「下降」，並帶有上次名次與本次名次。
5. **Given** 某 repo 同時存在於上次快照與本次榜單、且綜合名次完全未變，**When** 執行變化偵測，**Then** 該 repo 不出現在任何一類變化中。
6. **Given** 一個新進 repo 進入綜合 top 10 的 `#1`、把其下所有既有成員各推低 1 名，**When** 執行變化偵測，**Then** 這些被推低的 repo **全數列為「下降」**（純位移照實計為下降，不做同儕相對比較）。
7. **Given** 某 repo 存在於上次快照、但本次已不在綜合 top 10 中，**When** 執行變化偵測，**Then** 該 repo 不出現在任何一類變化中（當次靜默，亦不另報「跌出」）。
8. **Given** 某 repo 曾掉出 top 10、之後又重回綜合 top 10，**When** 執行變化偵測，**Then** 該 repo 以「新進」呈現。
9. **Given** 本次綜合 top 10 的成員與名次序列皆與上次快照完全相同，**When** 執行變化偵測，**Then** 輸出一個明確的「榜單無變化」結果（而非空白或錯誤），並可取得榜首 repo 供摘要呈現。
10. **Given** 某 repo 在上次與本次之間更名或轉移擁有者（識別碼不變），**When** 執行變化偵測，**Then** 系統仍視其為同一 repo，不會誤判為「新進」。

### User Story 2 - 榜單每七天才出現一次（Priority: P2）

擁有者每天都會收到晨報，但**不希望每天都被榜單洗版**。榜單段每七天才出現一次；未到期時，整段榜單處理直接跳過，當日只有新聞。計時基準是「上次榜單推播成功的時間」，而不是排程本身——所以即使某天排程漏跑或多跑，節奏也不會走鐘。到期門檻為 **162 小時**（七天減 6 小時寬限），使節奏穩定錨在每週同一時段。

**Why this priority**: 憲章原則 III 明訂榜單「由 `lastBoardPushAt` 計時（非 cron）」，且節奏須與「本週增星」這把七日尺一致——七天推一次，兩次比較的視窗才不重疊。它與 US1 可獨立驗證，但價值上略低於「變化偵測本身」——先要有正確的變化，才談得上多久呈現一次，故列 P2。

**Independent Test**: 給定不同的「上次榜單推播時間」（未到期 / 已到期 / 從未推播），檢視節奏判定是否分別為「跳過 / 執行 / 執行」；不依賴真實時間流逝（時間可注入）即可驗證。

**Acceptance Scenarios**:

1. **Given** 上次榜單推播距今未滿 162 小時，**When** 執行任務，**Then** 榜單段整段跳過，不進行榜單抓取、選榜或變化偵測，且狀態中的榜單快照維持不變。
2. **Given** 上次榜單推播距今已滿 162 小時或更久，**When** 執行任務，**Then** 榜單段照常執行變化偵測。
3. **Given** 從未推播過榜單（無上次推播時間），**When** 執行任務，**Then** 榜單段照常執行（視為已到期）。
4. **Given** 同一天內任務被觸發兩次、且第一次已成功推播榜單，**When** 第二次執行，**Then** 榜單段跳過（不重複推播）。
5. **Given** 上次榜單推播距今為 163 小時（即已過 6 天 19 小時、尚未滿七天整），**When** 執行任務，**Then** 榜單段照常執行——6 小時寬限使排程延遲不會把節奏往後推成第八天。
6. **Given** 「上次榜單推播時間」被寫成晚於當前時間的值（時鐘異常或人為誤植），**When** 執行任務，**Then** 榜單段視為已到期而照常執行，並發出告警，不會因負值間隔而永久靜默。

### User Story 3 - 狀態永遠可信、絕不半套（Priority: P3）

擁有者不必擔心「推播失敗但狀態已經寫掉」導致某次變化永遠消失。狀態只有在推播確實成功之後才寫回；推播失敗時狀態原封不動，下次執行仍會看到同一批變化。狀態檔本身是唯一權威來源，不會被繞過或出現寫到一半的內容。

**Why this priority**: 憲章原則 VI 的要害。它是正確性的護欄而非新能力，且在 US1／US2 成立後才有東西可寫回，故列 P3——但它是本 Feature 可視為完成的必要條件。

**Independent Test**: 模擬「推播成功」與「推播失敗」兩種結果，檢查狀態檔在前者被更新（快照 + 推播時間戳）、在後者完全未變；再連跑兩次，確認第二次只產出差異。

**Acceptance Scenarios**:

1. **Given** 變化偵測已產出結果、且後續推播回報成功，**When** 寫回狀態，**Then** 狀態中的榜單快照被更新為本次的綜合 top 10、且榜單推播時間戳被更新為本次時間。
2. **Given** 變化偵測已產出結果、但後續推播回報失敗，**When** 該次執行結束，**Then** 狀態中的榜單快照與榜單推播時間戳皆維持原值。
3. **Given** 一次成功的榜單推播已寫回狀態，**When** 立即以同一份榜單資料再跑一次變化偵測，**Then** 輸出為「榜單無變化」（第二次只產出差異）。
4. **Given** 某 repo 掉出綜合 top 10，**When** 寫回狀態，**Then** 該 repo 從榜單快照中移除，但其簡介快取不被清除。
5. **Given** 狀態寫回過程中途失敗，**When** 下次載入狀態，**Then** 讀到的是完整且有效的前一版狀態，不會是寫到一半的內容。

### Edge Cases

- **某領域候選不足保底席次**：某領域可用候選少於 2 筆時，該領域照實提供（1 筆或 0 筆），空出的席次由其他領域**依 FR-004 排序規則**遞補，綜合榜仍盡量補滿 10 席。
- **候選總數少於 10**：綜合榜照實呈現不足 10 筆，不強行湊數；名次為 `#1..#N`。
- **兩個 repo 估算週增星完全相同**：依 FR-004 的四層全序決勝（週增星 → 總星數 → 新進者優先 → repoId），名次必為穩定且可重現（同樣輸入必得同樣名次），不會因排序不穩定而在無實質變化時產生假的竄升／下降。
- **上次快照含已移除的領域值**：舊快照若帶有已不存在的領域分類，載入時不得使整個狀態失效或使流程崩潰。
- **上次推播時間戳為未來時間**（時鐘異常或人為誤植）：依 FR-019a 視為已到期並發告警，照常執行；下次成功推播即把時間戳改寫回正常值，自我修復。節奏判定不得因此永久卡死榜單段。
- **本次榜單為空**（上游來源全數失敗或全被過濾）：依 FR-025 中止榜單段——不產出變化結果、不推播、不寫回狀態，並發紅色告警；不得把「空榜」誤判成「全部掉出」而寫回空快照，亦不得推出誤導性的無變化摘要。新聞段照常。
- **上游連續多次全滅**：因空榜不寫回狀態，`lastBoardPushAt` 不動，榜單段會在其後**每次執行都判定到期而重試並再次告警**。此為 FR-025「自動重試」的直接推論，屬**已知且接受**的行為——重複告警正反映持續中的故障（不應被靜音），且重試的抓取量遠低於免費上限（憲章 I）。不引入告警抑制或退避。
- **榜單非空但候選嚴重不足**（如僅剩 2 筆）：**不**中止，照常選榜、diff 與呈現。曾評估「候選低於保底 4 席即中止」的門檻方案，於 2026-07-15 clarify **明確捨棄**——半殘榜確實會產生假掉出與假下降，但此噪音與 FR-010 已接受的純位移噪音同性質，捨棄可換得不必再多一個門檻常數與一組分支（一切從簡）。FR-025 的中止**僅**適用於完全為空。
- **同一 repo 在上次快照與本次榜單分屬不同領域**（歸類邊界移動）：仍以識別碼視為同一 repo，不得同時計為掉出與新進；其變化項目的所屬領域取**本次**的歸類（FR-015）。

## Clarifications

### Session 2026-07-15

本 Feature（F3）範圍內：

- Q: `RANK_JUMP_THRESHOLD`（T）取值為何？被新進 repo 擠下來的純位移（週增星未變、名次退 1）算不算下降？（開發指南 §11.2 明列此為 F3 待定項） → A: **T = 1，一律比較絕對綜合名次，兩方向對稱；純位移照實計為下降**。即「原本在榜上的 repo，名次只要前進就算竄升、只要後退就算下降」，不引入任何同儕相對比較。

  決策過程與理由（備查）：

  1. **位移問題是單向的**：新進 repo 只會把既有成員往下推，不可能往上推。故**絕對名次前進不可能是假的**——它必然代表原本排在其上的某個 repo 已落到其下（真實超車，或該 repo 掉出榜、意即週增星跌得更低）。**竄升側採 T=1 絕對名次零誤報**，不需要任何補償設計。
  2. **卡片顯示的是絕對名次**（`#9 → #3`，見開發指南 §5.3／§7）。若改用「共同成員相對名次」判定，會產出「🔺 竄升 `#5 → #6`」這種數字與箭頭互相矛盾的卡片（Z 確實超車 X，但同時進來兩個新人把 Z 由 #5 壓到 #6）。**絕對名次法在任何情況下都不會出現此矛盾**。
  3. **下降側明知有純位移噪音，仍選擇接受**：一個新進 repo 插進 `#1` 會使其下所有既有成員各退 1 名並全數列為下降。曾評估「絕對後退且相對名次亦後退才報」的濾除方案（可完全消除純位移），經評估後**明確捨棄——理由是實作與心智負擔的簡化優先**（使用者決策：「沒必要為了下降側另外設計和同儕對比的邏輯，我希望一切從簡」）。
  4. **與憲章 III「控制節奏、避免通知疲勞」的張力已評估、判定可接受**：張力為真但有界——(a) 變化視窗僅 10 席，故單次變化項目**恆 ≤ 10**（SC-004），不會無限膨脹；(b) **下降卡不帶簡介**（僅報名次變化，見開發指南 §5.3），故不消耗 LLM 額度、篇幅亦短；(c) 榜單**每七天才推一次**，非每日（本項於定案當時為「每三天」，節奏其後於同一 Session 改為每七天——推播更稀疏，故本張力只會更小，結論不變）。憲章 III 規範的是「只推變化、不重述整份榜單」與推播節奏，**未規定門檻值**，故 T=1 未違反非協商原則，屬本 Feature 權責內的參數選擇。
  5. **可逆**：T 為單一常數，日後若實測噪音過高，調整為 2 或 3 僅需改該常數、不動邏輯。先採最敏感值亦有助於觀測真實移動量。

- Q: FR-004 要求排名為確定性「含估算值相同時的決勝規則」，但該規則從未定義。決勝規則為何？ → A: **四層全序**——(1) 估算本週增星由高到低；(2) 相同則比**總星數**由高到低；(3) 再相同則**新進者優先**（不在上次快照者排在既有成員之前）；(4) 仍相同則比 **repoId 由小到大**（最終決勝）。

  補充（備查）：第 4 層保證任兩筆必分出高下，故排序為全序、`SC-008`（重跑 10 次名次 100% 一致）在任何輸入下皆成立，不依賴底層排序演算法是否穩定。第 3 層「新進者優先」在平手時會把既有成員推後一名、因而多產生一張下降卡；平手極罕見，且此代價與 FR-010 已接受的純位移噪音同性質，判定可接受。

- Q: 榜單推播節奏與「間隔如何量測」為何？（原訂三天；`lastBoardPushAt` 記錄的是推播完成時間，必晚於當次 cron 觸發時間，誤差單向累積會使節奏漂移） → A: **節奏由「每三天」改為「每七天」**；到期判定為 `now - lastBoardPushAt ≥ 162 小時`（168 小時減 6 小時寬限）。

  決策理由（備查）：

  1. **七天使比較視窗不重疊**：榜單的統一尺是「估算**本週**增星」（七日指標）。三天推一次等於用**重疊四天**的兩個七日視窗互比，兩次快照有超過一半是同一批星星，名次移動不能代表真實的週對週變化。七天節奏讓兩次比較的視窗剛好不重疊，「這週 vs 上週」才成立。
  2. **6 小時寬限沿用專案既有設計語彙**：新聞每日 guard 為「距今 < ~18h 即跳過」，即在 24 小時週期上留 6 小時寬限以吸收排程抖動。榜單的 168 小時週期沿用同一比例，吸收 GitHub Actions cron 延遲與 `:07`／`:37` 雙班抖動，使節奏穩定錨在每週同一時段而不單向漂移。
  3. **實作成本為零**：節奏為單一常數，取值 162h 與取值 72h 的邏輯完全相同。新聞每日晨報與 `lastNewsPushAt` guard 不受影響（兩條資料流本即解耦）。
  4. **真實來源同步**：「每三天」原載於憲章原則 III（非協商原則）、`docs/tech-radar-dev-guide.md` 與 `CLAUDE.md`。使用者已於 2026-07-15 明確授權將「三天 → 七天」同步修訂進上述三處真實來源（憲章修訂走 `/speckit-constitution`）。

  > 本 spec 開頭 **Input** 欄為使用者原始輸入的逐字存查紀錄，其中「每三天」「未滿三日」等敘述屬**修訂前**的原始措辭，不予改寫；節奏一律**以本節與 FR-017～FR-019 為準**。

- Q: 本次榜單為空（上游來源全數失敗或全被過濾）時，系統的行為為何？（Edge Cases 原僅載明「不得誤判為全部掉出」等禁止事項，Requirements 無對應 FR） → A: **空榜即中止榜單段**——不產出變化結果、不推播、不寫回任何榜單狀態，並發紅色告警；新聞段不受影響。

  理由（備查）：空榜代表上游全滅，屬**異常**而非「這週沒變化」，故不得走 FR-014 的「榜單無變化」路徑（該路徑要求提供榜首 repo，空榜並無榜首）。此行為忠於憲章原則 VII——「任一資料來源失敗不得使整條 pipeline 失敗」（新聞晨報照常）、「失敗須發紅色告警、不得無聲」。狀態不動 ⇒ `lastBoardPushAt` 不更新 ⇒ 下次執行仍視為已到期而自動重試，變化不會遺失。

- Q: 「上次榜單推播時間」晚於當前時間（時鐘異常或人為誤植）時，節奏判定的行為為何？（Edge Cases 原僅載明「不得永久卡死」，Requirements 無對應 FR） → A: **視為已到期並發告警**，照常執行榜單段。

  理由（備查）：推播不可能發生在未來，故未來時間戳是**不可能為真**的值，屬狀態毀損而非邊界情形。若不特判，`now - lastBoardPushAt` 為負值、恆小於 162 小時門檻，榜單段將**永久靜默且無任何告警**（跳過本身是正常路徑，不會觸發任何錯誤）。視為到期即解除死結；發告警使狀態毀損不會無聲（憲章原則 VII）；下一次成功推播會把時間戳改寫為正常值，**自我修復、不需修復程序**。

## Requirements *(mandatory)*

### Functional Requirements

**推播榜選取（跨領域綜合 top 10）**

- **FR-001**: 系統 MUST 把兩領域的當前榜單（追蹤深度：每領域至多 15 筆）合成**單一跨領域推播榜**，取前 10 筆，並指派 `#1..#10` 的綜合名次。
- **FR-002**: 系統 MUST 以**統一尺「估算本週增星」**作為跨領域排名依據，且 MUST 沿用 F2 已建立的同一把尺（含其「以總星數為上限」的約束），MUST NOT 另訂一套換算公式。FR-004 決勝規則第 2 層所用的總星數**僅在估算值相同時用於決勝**，不參與估算、不構成第二把尺，與本條不衝突。
- **FR-003**: 系統 MUST **保底每領域至少 2 席**：先為每個領域取**依 FR-004 決勝規則排序後最高的 2 筆**，其餘席次再跨領域**以同一套 FR-004 規則**擇優填入。領域候選不足 2 筆時照實取用，不得虛構條目。選榜全程 MUST 只使用 FR-004 這一套排序規則，MUST NOT 另引入「熱度」等未定義的替代判準。
- **FR-004**: 綜合榜的排名 MUST 是**確定性**的——相同輸入必產生相同名次。決勝規則 MUST 為以下**四層全序**，依序套用至分出高下為止：(1) 估算本週增星**由高到低**；(2) 總星數**由高到低**；(3) **新進者優先**（不在上次快照者排在既有成員之前）；(4) **repoId 由小到大**。第 (4) 層 MUST 保證任兩筆必分出高下，故排名 MUST NOT 依賴底層排序演算法是否穩定。因第 (3) 層依賴上次快照，綜合名次是「**當前榜單候選 + 上次快照**」兩者共同的函式——同一份候選搭配不同的上次快照，可能得到不同（但各自確定）的名次；SC-008 所稱的「相同輸入」即指此二者皆相同。
- **FR-005**: 系統 MUST NOT 把追蹤深度（兩領域合計至多 30 筆）寫入持久化狀態；持久化的榜單快照 MUST 只保留上次推播的綜合 top 10（至多 10 筆）。

**變化偵測**

- **FR-006**: 系統 MUST 以 repo 的**數字識別碼**（非名稱）判定「上次與本次是否為同一 repo」，使更名／轉移擁有者不影響同一性判定。
- **FR-007**: 系統 MUST 將「在本次綜合 top 10、但不在上次快照」的 repo 列為**新進**。
- **FR-008**: 系統 MUST 將「同時在上次快照與本次綜合 top 10、且**絕對綜合名次前進** ≥ `RANK_JUMP_THRESHOLD`」的 repo 列為**竄升**，並提供上次名次與本次名次。
- **FR-009**: 系統 MUST 將「同時在上次快照與本次綜合 top 10、且**絕對綜合名次後退** ≥ `RANK_JUMP_THRESHOLD`」的 repo 列為**下降**，並提供上次名次與本次名次。
- **FR-010**: `RANK_JUMP_THRESHOLD` MUST 為 **1**——名次只要移動即為變化，兩個方向對稱適用。名次比較 MUST 一律採**絕對綜合名次**（即卡片上呈現的 `#N`），MUST NOT 引入「共同成員相對名次」或任何同儕比較邏輯：**被新進 repo 擠下來的純位移照實計為下降**（決策與理由見 Clarifications Session 2026-07-15）。
- **FR-011**: 系統 MUST 將「在上次快照、但不在本次綜合 top 10」的 repo **當次靜默**：不列入任何變化類別、不另報「跌出」。
- **FR-012**: 系統 MUST 將「同時在上次快照與本次綜合 top 10、且絕對綜合名次**完全未變**」的 repo **當次靜默**：不列入任何變化類別。
- **FR-013**: 上次快照為空（冷啟動）時，系統 MUST 將本次綜合 top 10 全數列為新進，MUST NOT 採「靜默建立基準、不推播」的作法。
- **FR-014**: 三類變化皆為空**且本次綜合榜非空**時，系統 MUST 回傳一個明確的「**榜單無變化**」結果，且 MUST 提供榜首 repo 之**名稱、連結、所屬領域與估算本週增星**，供上層組成一行摘要。本次綜合榜為空時 MUST NOT 走本路徑（見 FR-025）。
- **FR-015**: 系統 MUST 為每個變化項目提供其**估算本週增星**與**所屬領域**，供上層呈現人氣落差與分類。所屬領域 MUST 一律取**本次榜單**的歸類結果；repo 於兩次之間跨越領域邊界時 MUST NOT 採用上次快照的領域值——變化項目呈現的是本次的榜單狀態，且上次快照的領域值可能來自已廢止的分類（見 FR-024）。
- **FR-016**: 系統 MUST 標示每個變化項目**是否需要簡介**（新進與竄升需要、下降不需要），但 MUST NOT 於本 Feature 生成或讀取簡介內容。

**每週節奏**

- **FR-017**: 系統 MUST 以狀態中的「**上次榜單推播時間**」與當前時間的間隔判定榜單段是否到期，MUST NOT 以排程本身或曆日作為節奏依據。到期門檻 MUST 為 **162 小時**（七天 168 小時減 6 小時寬限）——寬限用於吸收排程延遲與雙班抖動，使節奏穩定錨在每週同一時段而不單向漂移。
- **FR-018**: 榜單段未到期時，系統 MUST 整段跳過——不進行榜單抓取、選榜與變化偵測，且不變更榜單相關狀態。
- **FR-019**: 「上次榜單推播時間」不存在時，系統 MUST 視為已到期。
- **FR-019a**: 「上次榜單推播時間」**晚於當前時間**時（時鐘異常或人為誤植），系統 MUST 視為**已到期**並照常執行榜單段，且 MUST 就此發出**紅色告警**（與 FR-025 同一種告警——本專案不區分告警嚴重度）。系統 MUST NOT 因負值間隔恆低於門檻而使榜單段永久靜默。

**狀態與冪等**

- **FR-020**: 系統 MUST 僅在推播**確實成功之後**才寫回榜單快照與上次榜單推播時間；推播失敗時兩者 MUST 維持原值。
- **FR-021**: 系統 MUST NOT 寫入半套狀態——榜單快照與上次榜單推播時間 MUST 在同一次寫入中一併更新。
- **FR-022**: 系統 MUST 透過既有的單一狀態存取機制讀寫狀態，MUST NOT 繞過它直接改檔或另建平行狀態。
- **FR-023**: repo 掉出綜合 top 10 時，系統 MUST 將其自榜單快照移除，但 MUST NOT 清除其簡介快取。
- **FR-024**: 狀態中的榜單領域分類 MUST 對齊榜單現行的兩領域（AI / 前後端），並移除已廢止的 DevOps 分類；載入既有狀態時，MUST NOT 因舊分類值的存在而使整個狀態失效或中止流程。遇無法解析的快照條目時，系統 MUST 剔除該條目並**記錄警告**（MUST NOT 無聲剔除，憲章 VII），其餘條目照常載入。

**上游失效**

- **FR-025**: 本次綜合榜為**空**（上游來源全數失敗或候選全被過濾）時，系統 MUST **中止榜單段**——MUST NOT 產出變化結果、MUST NOT 推播、MUST NOT 寫回榜單快照或上次榜單推播時間。系統 MUST 就此發出紅色告警，MUST NOT 無聲略過；且 MUST NOT 使新聞段或整條 pipeline 失敗。因 `lastBoardPushAt` 未更新，下次執行 MUST 仍視為已到期而自動重試。

### Key Entities

- **榜單快照（Board Snapshot）**：上次推播的跨領域綜合 top 10。每筆代表一個 repo 在上次推播時的樣貌，關鍵屬性為：repo 數字識別碼（主鍵，用於跨執行比對）、repo 名稱與連結、**主要語言**、所屬領域、上次的估算本週增星、上次的綜合名次、首次被看到的時間。至多 10 筆；隸屬於唯一權威狀態。
- **推播榜（Push Board）**：本次執行由兩領域當前榜單合成的跨領域綜合 top 10，含每筆的綜合名次與估算本週增星。存在於單次執行期間，其內容在推播成功後才成為新的榜單快照。
- **榜單變化結果（Board Diff）**：本次與上次的比對產物，由三個互斥集合構成——新進、竄升、下降——外加一個「是否無變化」的判定與榜首摘要素材。掉出與穩定留榜者不屬於任何集合。
- **榜單節奏狀態（Board Cadence）**：上次榜單推播時間戳，隸屬於唯一權威狀態，是每週節奏（門檻 162 小時）的唯一計時基準。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: **在榜單段兩次皆到期的前提下**（節奏 guard 的行為另由 SC-002 涵蓋，不在本條範圍內），以同一份榜單資料連續執行兩次，第二次的榜單變化結果為「無變化」，產出的變化項目為 0 筆——即擁有者不會收到任何重述。
- **SC-002**: 上次榜單推播距今未滿 162 小時時，100% 的執行都會整段跳過榜單處理；距今已滿 162 小時或從未推播時，100% 的執行都會進行變化偵測。
- **SC-003**: 冷啟動（無上次快照）的首次執行，在**候選充足（歸類後候選總數 ≥ 10 筆）**時產出恰好 10 筆「新進」，且 0 筆竄升、0 筆下降。
- **SC-004**: 任一次執行產出的變化項目總數（新進 + 竄升 + 下降）不超過 10 筆。
- **SC-005**: **候選充足（每個領域各有 ≥ 2 筆歸類後候選）**時，綜合 top 10 中每個領域至少佔 2 席。
- **SC-006**: 推播回報失敗的執行，狀態檔內容 100% 與執行前逐位元組相同。
- **SC-007**: 上次快照中掉出綜合 top 10 的 repo，在該次變化結果中出現次數為 0；其簡介快取留存率 100%。
- **SC-008**: 相同輸入重複執行 10 次，綜合 top 10 的名次序列 100% 一致（無因排序不穩定而生的假變化）。此處的「**相同輸入**」指**當前榜單候選與上次快照兩者皆相同**——因 FR-004 決勝第 3 層依賴上次快照，名次是此二者共同的函式（見 FR-004）。驗證 MUST 包含「候選輸入順序被打亂」的情形。
- **SC-009**: 榜單快照的持久化筆數在任何時點皆不超過 10 筆。
- **SC-010**: 本次綜合榜為空的執行，100% 發出告警、且狀態檔內容與執行前逐位元組相同（0 筆變化項目、0 次推播）。

## Assumptions

- **上游榜單來源已就緒**：本 Feature 直接消費 F2 已驗收的「兩領域當前榜單（每領域至多 15 筆）」，不重新定義抓取與歸類邏輯。所消費的欄位為：**repo 數字識別碼、名稱與連結、所屬領域、估算本週增星、總星數、主要語言**——其中**總星數**為 FR-004 決勝第二層所需、**主要語言**為榜單快照持久化所需。此二欄皆為 F2 既有候選資料中已存在的值（F2 取得領域候選時即已一併取得），本 Feature 只需其**隨當前榜單一併帶出**，**不因此新增任何外部呼叫**（憲章 I）。
- **統一尺沿用 F2**：估算本週增星一律引用 F2 已建立、且已含「以總星數為上限」約束的同一把尺；本 Feature 不修改該公式。
- **狀態存取機制已就緒**：F1 已提供唯一權威狀態的原子讀寫（含壞檔擲錯不覆寫），本 Feature 沿用，不另建機制。
- **保底席次隨領域數縮放**：榜單領域已於 2026-07-15 由三個收斂為兩個，故「保底每領域 2 席」在本 Feature 為 **4 席保底 + 6 席跨領域競爭**。開發指南 §5.2 的示意程式碼仍寫著三領域時期的 `2×3=6`，屬過時註記，以憲章「保底每領域至少 2 席」的規則為準（此過時註記須於本 Feature 一併修正）。
- **無既有正式狀態需遷移**：目前狀態檔為空骨架、尚未有正式執行寫入過含 DevOps 分類的榜單資料，故領域分類收斂為兩領域屬型別對齊，不需要資料遷移程序（FR-024 的容錯僅為防禦性要求）。
- **推播由 F7 執行**：本 Feature 不組 Discord 版面、不發送訊息；「推播成功後才寫回」以「由上層告知推播結果、再由本 Feature 提供的狀態提交行為完成寫回」的方式滿足，端到端串接於 F7 驗收。
- **F3 階段的「交付成功」判準**：FR-020 的不變式是「**寫回一律發生在交付成功之後，交付失敗則狀態原封不動**」。本 Feature 單獨執行時尚無推播，其唯一的交付面是 log，故此階段的「交付成功」判準為**變化結果已成功產出並輸出到 log**；達成後即呼叫同一個狀態提交行為寫回（此即 SC-001「連跑兩次」得以在本階段驗證的前提）。F7 接上 Discord 後，觸發點改為「推播回報成功」，**狀態提交行為本身不變**。
- **簡介由 F5 生成**：本 Feature 只標示哪些變化項目需要簡介（新進與竄升），不生成也不讀取簡介內容；簡介快取的「不因跌出而清除」由本 Feature 在寫回狀態時保證。
- **時間可注入**：**全部**時間相關行為所依據的「當前時間」在測試中皆可被注入，不依賴真實時間流逝——涵蓋每週節奏判定、時間戳比較，以及狀態寫回時所用的推播時間與首次見到時間。
- **執行環境為一次性 CLI**：跑完即退，無常駐狀態；跨執行的記憶只有唯一權威狀態檔。
