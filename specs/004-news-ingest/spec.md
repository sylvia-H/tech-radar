# Feature Specification: 新聞來源設定與零 LLM 過濾漏斗（階段 A · News Ingest & Zero-LLM Funnel）

**Feature Branch**: `004-news-ingest`

**Created**: 2026-07-16

**Status**: Draft

**Input**: User description: "004-news-ingest"

> 範圍依真實來源界定：`docs/tech-radar-dev-guide.md` §4.1–4.3、§4.4 階段 A，以及 §11.2 的
> F4 條目。F4 交付「新聞來源設定檔 + 四種抓取器 + 正規化 + 零 LLM 的階段 A 漏斗」，把散落各來源
> 的原始項目收斂成一份**已去重、已過濾、大致無重複的候選清單（約 15～25 則）**，供 F6（階段 B，
> 單次 LLM 策展）取用。**本 Feature 不含**：任何 LLM 呼叫與策展（F6）、繁中 50/300 改寫（F6）、
> Discord 組版與推播（F7）、repo 簡介（F5）、榜單抓取與 diff（F2/F3，已驗收）。

## User Scenarios & Testing *(mandatory)*

本功能的「使用者」即專案擁有者（自用）。擁有者想每天讀到「對開發者最重要的幾則技術新聞」，
但新聞散落在十幾個來源、彼此大量重複（同一則新聞會同時出現在 HN、Reddit、Lobste.rs），且來源
清單會頻繁增刪修。本 Feature 建立**新聞資料流的前半段**：從**單一設定檔**讀取來源清單、逐一抓取、
正規化成統一結構，再用**零 LLM 的結構性手段**把跨來源重複與雜訊砍乾淨，最後產出一份收斂到約
15～25 則、大致無重複的候選清單。這份清單是 F6「每日只呼叫一次 LLM 策展」的輸入——**階段 A 把
重複與雜訊清乾淨，LLM 才能只花一次呼叫就挑出 6 則。**

本階段**只產出候選清單供觀測（log 可印出）**，不呼叫 LLM、不改寫成 50/300、不組 Discord 版面、
不推播——那些屬 F6 / F7。

### User Story 1 - 來源即設定：抓取與正規化只認一份清單（Priority: P1）

擁有者要增加、停用或替換一個新聞來源時，**只改一個設定檔**，不必碰任何抓取或處理程式碼；系統
會依清單抓取所有啟用中的來源，把各種格式（HN 的 JSON、Reddit/Lobste.rs 的 RSS、GitHub releases
的 Atom）統一正規化成同一種結構。任一來源解析到 0 筆時，系統**發出帶該來源識別碼的告警**，不無聲
略過；任一來源抓取失敗也不會拖垮其他來源。

**Why this priority**: 這是憲章原則 IV「新聞來源設定即資料」的直接實現，也是整條新聞資料流的地基
——沒有「從設定檔抓到正規化候選」，後面的去重、過濾、策展都無從談起。它本身即構成可展示的最小
可用產品：擁有者能看到「從我設定的來源抓到、正規化後的原始候選清單」。

**Independent Test**: 以幾個代表性來源（含四種類型各一）設定清單，執行抓取，檢視輸出是否為統一
結構的候選清單、`domain`／`tier` 正確取自設定；再把某來源設為停用、或新增一個來源，確認**只改
設定檔**即改變抓取結果、無須改動處理程式碼；並以「回傳 0 筆」的來源確認有發出帶識別碼的告警。

**Acceptance Scenarios**:

1. **Given** 設定檔含數個啟用中的來源（涵蓋四種抓取類型），**When** 執行抓取，**Then** 每個來源
   的項目被正規化為統一結構（至少含標題、目標連結、摘要節錄、來源識別碼、分數、領域、層級），
   且 `domain` 與 `tier` 直接取自該來源在設定檔中的設定。
2. **Given** 設定檔中某來源標記為停用，**When** 執行抓取，**Then** 該來源完全不被抓取，且無需
   改動任何處理程式碼。
3. **Given** 在設定檔新增一個合法來源，**When** 執行抓取，**Then** 該來源被納入抓取，且無需改動
   任何處理程式碼。
4. **Given** 某來源可連線但解析到 **0 筆**，**When** 執行抓取，**Then** 系統發出**帶該來源識別碼**
   的告警，並繼續處理其餘來源。
5. **Given** 某來源抓取失敗（逾時／連線錯誤／格式壞掉），**When** 執行抓取，**Then** 該來源被跳過
   並記錄，其餘來源照常抓取，整條新聞資料流不因單一來源失敗而中止。
6. **Given** 一個 GitHub releases 類型來源同時含 pre-release 與純 patch 版本，**When** 抓取該來源，
   **Then** pre-release 與純 patch 被濾除，只保留 major/minor 或安全修補，避免版本噪音灌爆候選池。
7. **Given** 一個屬 `cross` 的來源（如綜合社群聚合）產出未帶領域的項目，**When** 正規化，**Then**
   系統以關鍵字歸類法為其指派領域；非 `cross` 來源則直接沿用設定檔的領域，不重新歸類。

### User Story 2 - 跨來源去重：同一則新聞只留一筆（Priority: P1）

擁有者最痛的是「同一則新聞被十個來源各報一次」。系統對每則抽出其**目標連結**（新聞本體，而非
討論頁），正規化後以此為鍵合併——同一則跨來源只留一筆，保留分數最高者為代表、其餘來源記入該筆
的來源清單（供後續交叉驗證計數）。沒有共同目標連結時（例如兩篇不同部落格報同一件事），再用便宜
的標題近似度補一刀。整個去重過程**不呼叫任何 LLM**。

**Why this priority**: 這是本 Feature 與 F3 共同構成 M2 里程碑的驗收核心——「跨來源同一則新聞只
出現一筆、`sources[]` 正確合併」。它也是憲章原則 V「去重確實且節制 LLM」的地基：把絕大多數重複用
零 LLM 手段殺掉，才能把 LLM 用量鎖死在「每日一次」。沒有它，餵給 F6 的候選會充斥重複，污染策展
且浪費篇幅。與 US1 可獨立驗證：US1 產出原始候選，US2 對其去重。

**Independent Test**: 餵入一組**刻意包含跨來源重複**的正規化候選（同一目標連結出現在 HN／Reddit／
Lobste.rs、以及一組僅標題近似的不同連結），執行去重，檢視同一則是否只留一筆、代表項為分數最高
者、其餘來源併入來源清單且計數正確；全程不依賴 LLM 或真實網路。

**Acceptance Scenarios**:

1. **Given** 三個不同來源指向**同一個目標連結**（含不同的追蹤參數、大小寫、結尾斜線差異），
   **When** 執行去重，**Then** 只留一筆，且該筆的來源清單記錄全部三個來源。
2. **Given** 同一則新聞跨來源，各來源分數不同，**When** 合併，**Then** 保留**分數最高**者為代表項。
3. **Given** 兩筆目標連結不同、但標題正規化後 token 集合相似度超過門檻，**When** 執行標題近似
   去重，**Then** 兩筆被視為同一則並合併。
4. **Given** 兩筆目標連結不同、標題相似度低於門檻，**When** 執行去重，**Then** 兩筆維持獨立、
   不被誤合併。
5. **Given** 一筆帶追蹤參數與短網址轉址的連結，**When** 正規化目標連結，**Then** 追蹤參數被移除、
   host 小寫去 `www.`、結尾斜線統一、可低成本解開的短網址被解開，使指向同一資源者正規化為相同鍵。
6. **Given** 一則新聞在合併後其來源清單長度 ≥ 2，**When** 後續處理，**Then** 該筆被標記為**交叉
   驗證強訊號**（供 US3 加權）。

### User Story 3 - 階段 A 過濾與加權：把候選收斂到可策展的規模（Priority: P2）

去重之後仍有雜訊：低分的口水文、不重要的閒聊。系統以零 LLM 的規則做最後把關——低於品質門檻的
丟掉（門檻只作用於有社群分數的來源；一手官方來源不設分數門檻、天然視為強訊號），並對「多來源
交叉驗證」「提到當前榜上 repo」等訊號加權，讓候選最終收斂到約 15～25 則、大致無重複，等著交給
F6 的單次 LLM 策展。

**Why this priority**: 這一步把「去重後仍偏多、仍有雜訊」的清單收斂成 F6 可直接策展的規模。它建立
在 US2 的去重結果之上（P2 略低於去重本身），但沒有它，餵給 LLM 的候選會過多過吵。它同時落實憲章
原則 IV 的「Tier 2 一手來源不設分數門檻」與原則 V 的「結構性過濾為主力」。

**Independent Test**: 餵入一組已去重、帶不同分數與層級的候選（含 Tier 2 一手來源、含提到榜上 repo
者、含低分口水文），執行階段 A 過濾與加權，檢視：低分的 Tier 1/3 被丟、Tier 2 即使低分或單一來源
仍保留、交叉驗證與榜單相關項被加權、輸出規模落在預期區間；全程不依賴 LLM。

**Acceptance Scenarios**:

1. **Given** 一筆來自有社群分數來源（Tier 1/3）的候選、其正規化分數低於品質門檻，**When** 執行
   過濾，**Then** 該筆被丟棄。
2. **Given** 一筆來自一手官方來源（Tier 2，如 releases／官方公告）、無社群分數或分數為零，
   **When** 執行過濾，**Then** 該筆**不因分數門檻被丟**、直接保留為候選。
3. **Given** 一筆候選的來源清單長度 ≥ 2（多來源交叉驗證），**When** 加權，**Then** 其優先度被
   提升，較同分的單一來源項更可能入選。
4. **Given** 一筆候選的內容提到**當前 repo 榜單上的專案**，**When** 加權，**Then** 其優先度被提升。
5. **Given** 兩筆候選加權後分數相同，**When** 排序，**Then** 較新者排在前。
6. **Given** 一批已去重候選，**When** 完成階段 A 全部過濾與加權，**Then** 輸出為一份排序後的候選
   清單，規模收斂至可供單次 LLM 策展的範圍（目標約 15～25 則；候選稀少時照實輸出較少筆，不硬湊）。
7. **Given** Tier 3 選配來源的候選，**When** 過濾與加權，**Then** 適用**更高門檻與更低權重**，其對
   最終清單的邊際影響低於 Tier 1。

### User Story 4 - 只推新出現：不跨天重複回報（Priority: P3）

擁有者不希望昨天讀過的新聞今天又出現。系統記住已處理過的目標連結；已出現過的直接從候選排除。
這份「已見紀錄」會隨時間累積，故每次載入時把超過保留期（7 天）的舊紀錄修剪掉，避免無限膨脹。

**Why this priority**: 落實憲章原則 III／VI「只推變化、避免通知疲勞」在新聞側的跨天去重，並保住
狀態不膨脹。它是正確性與資訊品質的護欄而非新能力，且建立在候選清單已產出之後，故列 P3——但它是
本 Feature 可視為完成的必要條件。實際「寫回已見紀錄」的時機串接於 F6/F7（推播成功後），本 Feature
負責**消費**已見紀錄做排除、並負責**修剪**。

**Independent Test**: 給定一份已見紀錄（含在保留期內與超過保留期的項目）與一批候選（部分目標連結
已在紀錄中），執行載入修剪與排除，檢視：超過 7 天的紀錄被修剪、已見的候選被排除、未見的候選保留；
時間可注入，不依賴真實時間流逝。

**Acceptance Scenarios**:

1. **Given** 一批候選中某些目標連結已存在於已見紀錄，**When** 執行去歷史重複，**Then** 這些候選
   被排除、不進入輸出清單。
2. **Given** 已見紀錄含 `seenAt` 超過 7 天的項目，**When** 載入狀態，**Then** 這些逾期項目被修剪
   移除，紀錄不無限膨脹。
3. **Given** 已見紀錄含 `seenAt` 在 7 天內的項目，**When** 載入狀態，**Then** 這些項目被保留、
   仍用於排除。
4. **Given** 用於排除的已見連結與候選連結，**When** 比對，**Then** 一律使用**正規化後的目標連結**
   比對（與 US2 同一套正規化），使帶不同追蹤參數的同一連結仍被判為已見。

### Edge Cases

- **同一則新聞在同一來源內重複出現**（例如 feed 內含重複項）：去重同樣以正規化目標連結為鍵合併，
  不因「同來源」而略過。
- **某項目無可辨識的目標連結**（例如純討論貼、無外部連結）：以其自身的討論頁連結作為去重鍵、
  照常正規化，不得因缺目標連結而崩潰或被無聲丟棄。
- **標題近似去重的誤合併風險**：門檻設定須避免把「不同新聞但標題用字雷同」誤合併；門檻為可調
  參數，起始值偏保守，實測再校。
- **來源清單含重複識別碼或缺必填欄位**：設定檔 schema 驗證 MUST 擋下並明確報錯（識別碼是抓取
  告警與已見統計的引用鍵，不得重複或缺漏）。
- **所有來源同時失敗或全數解析 0 筆**：候選清單為空——本 Feature 照實輸出空清單並就每個 0 筆
  來源發告警；**不得**把空清單誤當成正常結果而無聲通過（每個 0 筆來源皆須告警）。新聞段之後
  如何處理空清單屬 F6/F7，不在本 Feature。
- **目標連結為短網址但無法低成本解開**：照實以短網址正規化後作為鍵，不為了解址而發起昂貴或
  不可靠的額外請求（抓取禮貌與零維運優先）。
- **Tier 2 來源解析到 0 筆**：與其他來源一致——發帶識別碼的告警（憲章 IV「解析到 0 筆必發告警」
  不因 tier 而例外），而非因「Tier 2 無分數門檻」就跳過告警。
- **候選提到榜上 repo，但當前執行無可用榜單資料**（例如榜單段未到期未建當前榜）：榜單相關性
  加權 MUST 在無榜單資料時安全略過（不加權），MUST NOT 崩潰或報錯。

  列舉合併與 `cross` 歸類（語意判斷交 LLM 更準、且不擴大 F4 範圍）。

## Requirements *(mandatory)*

### Functional Requirements

**來源設定即資料（憲章 IV）**

- **FR-001**: 所有新聞來源 MUST 集中於**單一設定檔**；增、刪、修來源 MUST 只改此設定檔，
  MUST NOT 改動任何抓取或漏斗處理程式碼。
- **FR-002**: 每個來源設定 MUST 至少包含：唯一識別碼、抓取類型、來源位址、領域、層級（tier），
  並可選擇性標記啟用/停用（未標記時預設啟用）。系統 MUST 對來源清單做 schema 驗證，遇識別碼
  重複或必填欄位缺漏 MUST 明確報錯，MUST NOT 靜默載入不合法清單。
- **FR-003**: 系統 MUST 只抓取標記為啟用的來源；標記停用的來源 MUST 被完整略過。
- **FR-004**: 系統 MUST 支援四種抓取類型：HN（Algolia 查詢）、Reddit 週熱門（RSS）、一般 RSS、
  GitHub releases（Atom）。新增同類型來源 MUST 只需在設定檔加一筆，MUST NOT 改動處理程式碼。

**抓取與正規化**

- **FR-005**: 系統 MUST 把各來源的原始項目正規化為**統一結構**，至少含：標題、**目標連結**（新聞
  本體連結，而非討論頁 permalink；MUST 同時保留**正規化後鍵值**（去重主鍵，見 FR-011）與**正規化前
  原值**（供輸出／觀測））、摘要節錄、來源識別碼、分數、領域、層級、以及一個「來源清單」
  欄位（去重合併時記錄同一則的多個來源）。
- **FR-006**: 正規化時，`domain` 與 `tier` MUST 直接取自來源設定檔；**僅 `cross` 來源**（其項目
  跨領域、無法由來源本身決定領域）MUST 以關鍵字歸類法指派領域，非 `cross` 來源 MUST NOT 重新歸類。
- **FR-007**: 摘要節錄 MUST 取自來源 feed 的摘要／描述並截斷至合理長度（供 F6 階段 B 產出內容的
  素材），MUST NOT 於本 Feature 呼叫 LLM 改寫或補充來源未提供的內容。
- **FR-008**: GitHub releases 類型抓取 MUST 濾除 pre-release 與純 patch 版本，只保留 major/minor
  或安全修補，避免版本噪音灌爆候選池。
- **FR-009**: 抓取 MUST 遵守抓取禮貌：帶自訂 User-Agent、盡量使用條件式請求（ETag／
  If-Modified-Since）、失敗採指數退避重試。
- **FR-010**: 候選時間軸 MUST 對齊「近一週」視角：Reddit 取週熱門（`t=week`）、HN 過濾近 7 天
  （`created_at_i`）。**GitHub releases** 因 `releases.atom` 僅回最新數筆、天然偏近期，MUST NOT
  為其另加逐筆日期過濾（避免無謂邏輯）——其近期性由 feed 天然近況 ＋ 版本過濾（FR-008）共同界定；
  一般 RSS（官方 blog）亦不強制日期窗。以上殘留的偏舊項由新鮮度決勝（FR-020）與 F6 策展處理。

**去重（零 LLM，憲章 V）**

- **FR-011**: 系統 MUST 對每則抽出其**目標連結**並正規化後作為去重鍵；正規化 MUST 至少包含：
  host 小寫、去 `www.`、統一結尾斜線、移除追蹤參數（如 `utm_*`／`ref`／`fbclid`／`gclid`）、
  以及可低成本解開的常見短網址／轉址。指向同一資源者 MUST 正規化為相同鍵。
- **FR-012**: 以正規化目標連結為鍵合併時，系統 MUST 只保留一筆、以**分數最高者為代表項**（比較時
  `null` 分數視為低於任何數值），其餘來源 MUST 併入該筆的來源清單。**分數相同（含皆為 `null`）時**，
  代表項 MUST 以確定性決勝選出——`sourceId` 字典序、再 `originalUrl` 字典序取最小者——使相同輸入下
  代表項唯一、不依賴輸入順序（SC-011）。
- **FR-013**: 對無共同目標連結者，系統 MUST 以**標題近似度**補漏去重：標題正規化（去符號、小寫、
  去 stop words）後計算 token 集合相似度，超過門檻即視為同一則並合併。門檻 MUST 為可調參數。
- **FR-014**: 去重 MUST 全程不呼叫任何 LLM，MUST NOT 引入向量檢索／embeddings。
- **FR-015**: 無可辨識目標連結的項目（如純討論貼），系統 MUST 以其自身連結作為去重鍵照常處理，
  MUST NOT 因缺目標連結而崩潰或無聲丟棄。

**階段 A 過濾與加權**

- **FR-016**: 系統 MUST 對**有社群分數的來源（Tier 1／Tier 3）**套用品質門檻，低於門檻者丟棄；
  門檻 MUST 為可調參數。**Tier 2 一手來源 MUST NOT 套用分數門檻**（無社群分數，天然視為強訊號）。
- **FR-017**: 系統 MUST 對「來源清單長度 ≥ 2」（多來源交叉驗證）的候選加權，使其優先於同分的
  單一來源項。Tier 2 項目即使為單一來源，MUST 亦視為強訊號。
- **FR-018**: 系統 MUST 對「內容提到當前 repo 榜單上的專案」的候選加權；當前無可用榜單資料時，
  此加權 MUST 安全略過，MUST NOT 崩潰或報錯。
- **FR-019**: 系統 MUST 依 tier 差異化加權：Tier 3 選配來源套用**更高門檻與更低權重**，Tier 1
  為標準門檻與權重。
- **FR-020**: 加權後分數相同時，系統 MUST 以**新鮮度**決勝（較新者在前）。
- **FR-021**: 階段 A 全部處理完成後，系統 MUST 產出一份**排序後、大致無重複**的候選清單，其規模
  MUST 收斂至可供單次 LLM 策展的範圍（目標約 15～25 則）；候選稀少時 MUST 照實輸出較少筆，
  MUST NOT 硬湊。

**去歷史重複與狀態修剪（憲章 III／VI）**

- **FR-022**: 系統 MUST 以**正規化後的目標連結**（與 FR-011 同一套正規化）比對已見紀錄，將已出現
  過的候選自輸出排除。
- **FR-023**: 系統 MUST 在載入狀態時修剪已見紀錄中 `seenAt` 超過保留期（**7 天**）的項目，使該
  紀錄不無限膨脹；保留期內的項目 MUST 保留並用於排除。
- **FR-024**: 本 Feature MUST 透過既有的單一狀態存取機制讀取與修剪已見紀錄，MUST NOT 繞過它
  直接改檔或另建平行狀態。**寫回**新的已見紀錄（即把本次入選項標記為已見）之時機屬 F6／F7
  （推播成功後才寫回），本 Feature MUST NOT 於候選產出階段就把候選寫入已見紀錄。

**容錯（憲章 IV／VII）**

- **FR-025**: 任一來源解析到 **0 筆** 時，系統 MUST 發出**帶該來源識別碼**的告警，MUST NOT 無聲
  略過；此規則對所有 tier 一致，Tier 2 不例外。
- **FR-026**: 任一來源抓取或解析失敗時，系統 MUST 跳過該來源並記錄，MUST NOT 使其餘來源或整條
  新聞資料流失敗（來源隔離容錯）。

**領域分類法（Clarifications 2026-07-16 定案）**

- **FR-027**: 新聞候選的 `domain` 列舉 MUST 為 `ai | devops | frontend-backend | cross`（比照榜單
  合併前後端）。MUST 保留 **`devops`**（憲章 v1.2.0 Scope note：榜單移除 DevOps 不連帶移除新聞的
  devops；配額與三個 DevOps 專屬來源皆不變）。依 FR-006 對 `cross` 來源做關鍵字歸類時，前後端相關
  項 MUST 一律歸入單一 `frontend-backend` 桶，MUST NOT 再細分 backend／frontend。
- **FR-028**: 「後端只收 Node.js／Python、前端以 TypeScript 為主、不收 CSS 技巧／教學」等**主題
  降噪規則**於本 Feature（階段 A）MUST NOT 以關鍵字硬篩實作；此類語意判斷 MUST 留待 F6 階段 B 的
  單次 LLM 策展外顯執行（見 dev-guide §4.4 階段 B）。本 Feature 對前後端內容一律先歸入
  `frontend-backend` 候選，交由階段 B 依開發者重要性取捨。

### Key Entities

- **新聞來源（News Source）**：設定檔中的一筆來源定義。關鍵屬性：唯一識別碼（抓取告警與已見統計
  的引用鍵）、抓取類型、來源位址、領域、層級（tier 1/2/3）、啟用旗標。來源清單是新聞資料流的
  唯一設定入口（憲章 IV）。
- **新聞候選（News Candidate）**：正規化後的統一結構，代表一則潛在入選新聞。關鍵屬性：標題、
  正規化目標連結（去重主鍵）、摘要節錄、來源識別碼、分數、領域、層級、來源清單（合併後的多來源
  紀錄，長度 ≥ 2 即交叉驗證強訊號）、新鮮度時間。存在於單次執行期間。
- **已見新聞紀錄（Seen News）**：跨執行持久化於唯一權威狀態的清單，每筆為 `{正規化目標連結,
  seenAt 時間戳}`，用於跨天去重排除與 7 天修剪。本 Feature 只消費與修剪，寫回屬 F6/F7。
- **候選清單（Candidate Set）**：階段 A 的最終產物——一份排序後、大致無重複、收斂至約 15～25 則
  的候選集合，作為 F6 單次 LLM 策展的輸入。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 對一組刻意包含跨來源重複（同一目標連結出現在 ≥ 3 個來源）的輸入，去重後**同一則
  只出現一筆**，且其來源清單完整合併全部來源（M2 驗收核心）。
- **SC-002**: 新增或停用一個來源**只需修改設定檔**、不需改動任何處理程式碼，即改變抓取行為
  （可由「僅設定檔 diff」證明）。
- **SC-003**: 任一來源解析到 0 筆時，100% 發出帶該來源識別碼的告警（含 Tier 2 來源）。
- **SC-004**: 任一來源抓取失敗時，其餘來源仍 100% 被抓取，整條新聞資料流不中止。
- **SC-005**: Tier 2 一手來源即使分數為零或缺分數，被分數門檻丟棄的比率為 **0%**。
- **SC-006**: 對一組代表性輸入，階段 A 輸出的候選清單規模收斂至約 15～25 則的目標區間（候選充足
  時）；候選稀少時輸出實際數量、不硬湊。
- **SC-007**: 已存在於已見紀錄（保留期內）的目標連結，在候選輸出中出現次數為 **0**（跨天不重複）。
- **SC-008**: 已見紀錄中 `seenAt` 超過 7 天的項目，載入後留存率為 **0%**（100% 被修剪）。
- **SC-009**: 帶不同追蹤參數／大小寫／結尾斜線但指向同一資源的連結，正規化後 100% 得到相同的
  去重鍵（不因表面差異而漏去重）。
- **SC-010**: GitHub releases 來源中的 pre-release 與純 patch 版本，在候選輸出中出現次數為 **0**。
- **SC-011**: 相同輸入重複執行多次，去重與過濾後的候選清單（成員與排序）100% 一致（確定性、
  不依賴排序穩定性）。

## Assumptions

- **狀態存取機制已就緒**：F1 已提供唯一權威狀態的原子讀寫；`seenNews` 欄位（`{url, seenAt}` 陣列）
  已存在於狀態 schema，本 Feature 沿用，不另建機制。
- **當前榜單資料由上游提供**：FR-018 的「榜單相關性加權」消費**當前執行已建的榜單**（若該次
  榜單段有執行）或既有狀態中的榜單快照；本 Feature 不重新抓取或建構榜單，且在無榜單資料時安全
  略過加權。榜單抓取與 diff 屬 F2/F3（已驗收）。
- **LLM 屬 F6**：本 Feature 全程零 LLM——不呼叫策展、不做語意去重、不改寫成 50/300、不用 embeddings。
  殘留語意重複由 F6 的單次策展呼叫順手清除；本 Feature 只負責結構性去重與過濾。
- **推播與已見寫回屬 F6/F7**：本 Feature 產出候選清單供觀測（log 可印出）；把入選項標記為已見並
  寫回狀態的時機是「推播成功後」，串接於 F6/F7，本 Feature 不執行。
- **抓取類型釘死為四種**：`hn-algolia`／`reddit-weekly`／`rss`／`github-releases`，對應 dev-guide
  §4.2 的初始來源清單；新增來源只在既有四種類型內擴充，不新增抓取類型即屬設定檔變更。
- **feed URL 上線前逐一驗證**：dev-guide §4.3 要求上線前確認每個 feed URL 可用；壞掉的 feed 以
  設定檔停用／替換處理，不動 code。
- **時間可注入**：全部時間相關行為（近 7 天口徑、已見紀錄 7 天修剪、新鮮度決勝）所依據的「當前
  時間」在測試中皆可被注入，不依賴真實時間流逝。
- **門檻值為可調的起始值**：品質分數門檻（如 HN／Reddit／Lobste.rs 的起始建議值）與標題近似度
  門檻皆為可調參數，dev-guide §4.4 提供起始值，實測再校，不視為硬性契約。
- **執行環境為一次性 CLI**：跑完即退，無常駐狀態；跨執行的記憶只有唯一權威狀態檔。
