# Feature Specification: GitHub Pages 儀表板 + RSS/Atom 發佈

**Feature Branch**: `008-pages-publish`

**Created**: 2026-08-04

**Status**: Draft

**Input**: User description: "feature 008-pages-publish"

## Clarifications

### Session 2026-08-04

- Q: 發佈所需的資料（今日精選新聞全文、上次榜單變化摘要、滾動 feed 歷史）要如何取得與持久化？
  → A: 在 `state/board.json` 新增發佈用欄位，由**核心推播段**推播成功後一併寫入，發佈段全程
  唯讀；新欄位一律為選用欄位（既有 state 檔須能無錯載入）、網頁須標示該批新聞的產生時間、
  feed entry 不攜帶星數。
- Q: 榜單事件（新進／竄升）的 feed entry 識別鍵如何構成？ → A: `repoId` ＋ 事件型別 ＋ 事件日期
  （例 `repo:{repoId}:new:2026-08-04`）。同一次事件的識別鍵跨執行穩定不變；repo 日後重回榜或
  再次竄升因日期不同而正確產生新 entry，對齊憲章原則 III「日後重回即以新進呈現」。
- Q: 網頁的榜單區塊呈現哪些 repo？ → A: 呈現 `state/board.json` 現有的**跨領域綜合 top 10**
  （即最近一次推去 Discord 的同一份榜），在版面上依領域分成 AI、前後端兩區顯示，沿用推播的名次；
  不呈現每領域追蹤深度（top 15）中未進入推播榜的 repo。
- Q: 發佈段被跳過或失敗時，告警行為如何？ → A: 區分預期與異常——repo 為 private 而跳過屬預期
  行為，靜默不告警（只留執行日誌）；可見性查詢本身失敗、以及發佈執行失敗屬異常，MUST 發紅色
  告警 embed 到告警頻道（憲章 VII「不得無聲失敗」）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 免 Discord 瀏覽當前雷達快照 (Priority: P1)

一位對這份雷達感興趣、但沒有加入該 Discord 伺服器的訪客，直接開啟公開網址，就能在同一頁看到
目前的推播榜（跨領域綜合 top 10，依 AI／前後端兩領域分區顯示、含快取簡介）、上次榜單變化摘要，
以及今日精選新聞（標題＋內容），內容呈現與 Discord 推播的繁體中文版一致。

**Why this priority**: 這是本 Feature 的核心價值——讓雷達的產出不再鎖在單一 Discord 伺服器內；
沒有這個頁面，其餘（feed 訂閱、隱私停用）都無從談起。

**Independent Test**: 在 repo 為 public 且已有至少一次成功的榜單／新聞推播後，直接以瀏覽器開啟
發佈網址，可看到與當次 Discord 推播內容一致的榜單與新聞，且不需要任何 Discord 存取權限。

**Acceptance Scenarios**:

1. **Given** repo 為 public、且 `state/board.json` 已有榜單快照與今日新聞精選，**When** 排程執行完
   核心推播段後觸發發佈，**Then** 公開頁面呈現推播榜 top 10（依 AI／前後端分區、含簡介）、上次
   榜單變化摘要、今日精選新聞，且文字內容與當次推去 Discord 的版本一致（同一批已去重、已精選的
   資料，非另行產生）。
2. **Given** 尚未有任何一次成功推播（`state/board.json` 為初始空骨架），**When** 觸發發佈，
   **Then** 頁面仍可正常呈現（顯示「尚無資料」等空狀態），不得因空狀態而使發佈流程失敗。
3. **Given** 當日新聞來源全數失敗、頁面沿用的是前一日已推播的那批精選新聞，**When** 訪客開啟
   頁面，**Then** 新聞區塊明確標示該批內容的產生時間（即前一日），使訪客能分辨這不是當日產出
   （FR-015 的驗收點）。

### User Story 2 - 以 RSS/Atom 訂閱雷達更新 (Priority: P2)

一位習慣用 RSS reader 追蹤資訊源的使用者，訂閱雷達提供的 feed，之後每次雷達有新的精選新聞、
新進榜 repo 或竄升 repo 時，reader 會顯示一則新 entry；同一事件不會因為排程重複執行而被顯示
兩次。

**Why this priority**: 讓雷達的更新可以被動推送到訪客既有的閱讀工作流程，而不需要每天主動回訪
網頁；重要性次於「頁面本身要能看」，故列 P2。

**Independent Test**: 以任一主流 RSS/Atom 閱讀器訂閱 feed 網址，可正確解析並顯示 entry 清單；
針對同一則新聞或同一個榜單事件，即便排程重複執行多次，reader 中仍只出現一次。

**Acceptance Scenarios**:

1. **Given** 今日新聞精選已產出、且 repo 為 public，**When** 核心推播段將該批新聞加入 feed 歷史
   後觸發發佈，**Then** 發佈出的 feed 含對應 entry，且每則 entry 的識別在後續執行中保持穩定
   （不因重跑而改變或重複出現）。
2. **Given** 上次榜單推播出現「新進榜」或「竄升」的 repo，**When** 觸發發佈，**Then** 發佈出的
   feed 含對應 entry；「跌出榜」不產生 entry（與 Discord 推播的靜默規則一致）。
3. **Given** feed 歷史累積的 entry 數超過 50 筆上限，**When** 核心推播段寫入新 entry，**Then**
   最舊的 entry 被移除，feed 檔案大小不無限成長。
4. **Given** 某 repo 曾以「新進榜」進入 feed、之後掉出推播榜，**When** 該 repo 於日後某週重回
   榜單並被再次推播，**Then** feed 新增一則識別鍵不同的新 entry，reader 會再次顯示，而非被視為
   重複而靜默。
5. **Given** feed 內已累積多則榜單事件 entry，**When** 檢視發佈出的 feed 內容，**Then** 每則
   entry 只帶標題、連結、時間與事件型別，**不含星數／週增星等任何數值指標**——使 feed 歷史
   無法被還原成一份星星時序資料（FR-016 的驗收點，對齊憲章原則 II）。

### User Story 3 - repo 轉為 private 時自動停止發佈 (Priority: P3)

專案擁有者把 repo 從 public 切換為 private（例如暫時不想公開）。下一次排程執行時，網站與 feed
的發佈**自動停止**，不需要另外手動關閉任何開關；同時 Discord 推播與狀態記錄完全不受影響，照常
運作。

**Why this priority**: 這是隱私安全的必要防線，但只在 repo 曾經公開又被收回時才會觸發，發生頻率
低於前兩個故事，故列 P3；然而一旦發生若未正確停用，後果是機密外洩風險，因此仍是本 Feature
必須具備的能力，不可省略。

**Independent Test**: 將測試用 repo 可見性模擬為 private，觸發一次執行，確認發佈階段被跳過（不
產生/不更新網站與 feed 產物），同時確認同一次執行中 Discord 推播與 `state/board.json` 寫入結果
與「發佈段不存在」時完全相同。

**Acceptance Scenarios**:

1. **Given** repo 可見性查詢結果為 private，**When** 執行到發佈階段，**Then** 該階段整段跳過
   （不產生頁面、不更新 feed、不部署），且不記錄為失敗。
2. **Given** 發佈階段本身發生錯誤（例如部署當下失敗），**When** 該次執行的核心推播段已成功完成，
   **Then** 錯誤不得回滾已寫入的狀態、不得使已送達的 Discord 推播被判定失敗，僅該次發佈本身
   未更新，並依 FR-017 發出紅色告警。
3. **Given** repo 稍後由 private 改回 public，**When** 下一次排程執行，**Then** 發佈自動恢復
   （不需要任何人工重新啟用的操作）。

---

### Edge Cases

- repo 可見性查詢本身失敗（例如 API 暫時無法回應）時，發佈階段應視同「無法確認為 public」而跳過
  本次發佈，不得預設為 public 貿然發佈；不得影響核心推播段。此情形屬異常，須依 FR-017 發送告警，
  以免查詢持續失敗導致發佈長期停擺而無人知曉。
- 核心推播段本次因節奏未到期而跳過（例如榜單未到 162 小時門檻、新聞已推播過 idempotency guard
  生效）時，網站與 feed 應沿用 `state/board.json` 現有內容重新產生（呈現上一次已推播的快照），
  而非顯示空白或報錯。
- 核心推播段部分失敗（例如新聞來源全數失敗導致當日無新聞可選）時，發佈仍應以現有可用的狀態內容
  正常產生頁面／feed，不得因單一區塊缺資料而整頁失敗。
- feed entry 的識別鍵在新聞與榜單事件之間為不同語意（新聞＝正規化目標 URL、榜單＝`repoId`＋事件
  型別＋事件日期），需確保兩種來源各自穩定去重、彼此不衝突（例如以型別前綴區隔命名空間）。
- 同一 repo 掉出推播榜後於日後重回、或在不同週再次竄升時，MUST 產生新的 feed entry 而非被視為
  重複事件而靜默——此為與「重跑不重複」相對的另一側失效模式，兩者須同時成立。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系統 MUST 在 repo 為 public 時，發佈一個公開可瀏覽的網頁，呈現 `state/board.json`
  現有的推播榜（跨領域綜合 top 10，含各 repo 快取簡介），在版面上依領域分成 AI、前後端兩區、
  沿用推播名次；並呈現上次榜單變化摘要。網頁 MUST NOT 呈現未進入推播榜的追蹤深度 repo。
- **FR-002**: 系統 MUST 在同一網頁呈現今日精選新聞（標題＋內容），內容與同次已送達 Discord 的
  版本一致——重用同一批已去重、已精選、已套用字數上限的資料，不得為網頁另行挑選或改寫。
- **FR-003**: 系統 MUST 發佈一份可訂閱的 feed，涵蓋三類事件：今日精選新聞、新進榜 repo、榜單
  竄升 repo；「跌出榜」不產生 feed entry（與現行 Discord 推播的靜默規則一致）。
- **FR-004**: 系統 MUST 為每則 feed entry 使用跨執行穩定的識別鍵，使遵循 RSS/Atom 規範的閱讀器
  能對同一事件自動去重、不重複顯示：新聞以正規化目標 URL；榜單事件以 `repoId` ＋ 事件型別
  （新進／竄升）＋ 事件日期的組合。榜單識別鍵 MUST 含事件型別與日期——同一 repo 掉出榜後重回、
  或在不同週再次竄升，屬**不同事件**，MUST 各自產生獨立 entry（對齊憲章原則 III「日後重回即以
  新進呈現」）。
- **FR-005**: 系統 MUST 將 feed 的歷史 entry 數量控制在 **50 筆**的上限內，超出上限時移除最舊的
  entry，避免 feed 內容無限成長。該歷史清單持久化於 `state/board.json` 的發佈用欄位，沿用既有
  `seenNews` 的滾動修剪模式。
- **FR-006**: 系統 MUST 在每次觸發發佈前查詢 repo 可見性；查詢結果為 private、或查詢本身失敗
  無法確認為 public 時，MUST 完整跳過本次發佈（不產生也不更新任何發佈產物）。
- **FR-007**: 系統 MUST 將發佈流程與核心推播流程（Discord 推播、`state/board.json` 寫入）完全
  隔離：發佈被跳過或發佈本身失敗，都 MUST NOT 影響核心推播段的執行結果、MUST NOT 回滾已寫入的
  狀態、MUST NOT 使 Discord 推播被視為失敗。發佈段對 `state/board.json` **唯讀**——所有發佈所需
  資料一律由核心推播段寫入（見 FR-013），發佈段 MUST NOT 寫入任何狀態。
- **FR-008**: 發佈產物 MUST NOT 包含任何機密（API token、Discord webhook URL 等），且 MUST NOT
  包含任何未曾透過 Discord 推播對外揭露過的資訊。
- **FR-009**: 網頁與 feed 呈現的領域範圍、排序邏輯與文字長度上限（標題／內容／簡介）MUST 與
  既有 Discord 推播的規則完全一致，不得為發佈另訂一套內容政策。
- **FR-010**: 系統 MUST NOT 為了產生網頁或 feed 內容而新增任何 LLM 呼叫；發佈階段必須零 LLM
  用量，完全重用核心推播段已產出的結果。
- **FR-011**: 系統 MUST NOT 為網頁或 feed 額外存放或運算逐日星星走勢一類的歷史時序資料（不新增
  自存星星歷史）。
- **FR-012**: 當核心推播段本次因節奏門檻或 idempotency guard 而跳過時，系統 MUST 仍以
  `state/board.json` 現有內容重新產生網頁與 feed（呈現上一次已推播的快照），不得顯示空白或視為
  錯誤。
- **FR-013**: 核心推播段 MUST 在推播成功後，將發佈所需資料一併寫入 `state/board.json`：最近一次
  晨報的精選新聞全文（標題＋內容）、最近一次榜單變化摘要、滾動 feed 歷史清單。此寫入 MUST 與
  既有狀態寫回屬同一次原子寫入，不得產生半套狀態（憲章 VI）。
- **FR-014**: FR-013 新增的狀態欄位 MUST 為選用欄位——不含這些欄位的既有狀態檔 MUST 能無錯載入，
  且 MUST NOT 因缺少這些欄位而使核心推播段失敗。
- **FR-015**: 網頁 MUST 標示所呈現之精選新聞批次的產生時間，使訪客能分辨該批內容是否為當日產出
  （沿用上一次已推播批次時尤其必要）。
- **FR-016**: feed entry MUST NOT 攜帶星數等數值指標，避免 feed 歷史累積成一份事實上的星星時序
  資料（與 FR-011「不新增自存星星歷史」一致）。
- **FR-017**: 發佈段因 repo 為 private 而跳過時，MUST NOT 發送告警（屬預期行為，僅寫入執行日誌）；
  可見性查詢本身失敗、或發佈執行失敗時，MUST 發送紅色告警 embed 至告警頻道，不得無聲失敗
  （憲章原則 VII）。「發佈執行失敗」涵蓋渲染／寫檔失敗，**亦涵蓋**網頁與 feed 部署動作本身失敗
  （即便該動作是發佈流程的最後一步、跑在渲染／寫檔之後）。該告警 MUST NOT 影響核心推播段的成功
  判定（FR-007）。

### Key Entities *(include if feature involves data)*

- **儀表板頁面**：單一公開網頁，呈現「目前推播榜（綜合 top 10，依領域分區）＋簡介」「上次榜單
  變化摘要」「今日精選新聞（含批次產生時間）」三個區塊；為單一當前快照，非逐日歷史封存頁。
- **Feed**：可訂閱的更新清單，由多筆 entry 組成，保留上限 50 筆的滾動清單。
- **Feed entry**：單一可訂閱事件，型別為「新聞」或「榜單變化（新進／竄升）」，帶跨執行穩定的
  識別鍵、標題、對應連結、產生時間；不含星數等數值指標。
- **發佈用狀態欄位**：`state/board.json` 內新增的選用欄位，存放最近一次晨報的精選新聞全文、最近
  一次榜單變化摘要與滾動 feed 歷史清單；由核心推播段寫入、發佈段唯讀。
- **可見性狀態**：repo 目前是否為 public 的查詢結果，決定本次是否執行發佈階段。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 造訪公開網址的訪客，不需任何 Discord 帳號或伺服器成員資格，即可在單一頁面看到
  當前榜單與今日精選新聞。
- **SC-002**: 使用任一遵循 RSS/Atom 規範的閱讀器訂閱 feed 後，同一事件不因排程重複執行而在
  閱讀器中重複出現。
- **SC-003**: repo 由 public 切換為 private 之後的下一次排程執行，網站與 feed 停止更新；同一
  期間 Discord 推播的送達結果與 `state/board.json` 寫入結果，與「未啟用發佈功能」時完全相同。
- **SC-004**: 任何一次發佈階段的失敗或跳過，造成的 Discord 推播失敗次數為零——即發佈段的成敗
  完全不影響核心推播段的成功率。
- **SC-005**: 發佈功能上線後，每日 LLM 呼叫次數維持不變（不因新增網頁／feed 而增加任何一次
  呼叫）。
- **SC-006**: 同一 repo 掉出推播榜後於日後重回榜並被推播時，訂閱者的閱讀器會顯示為一則新 entry
  ——「重跑不重複」與「重回榜要再現」兩項同時成立，不因去重而漏掉合法的第二次事件。
- **SC-007**: 發佈功能上線後，既有的 `state/board.json`（不含發佈用欄位）能被無錯載入，核心
  推播段的成功率不因 state 結構變更而下降。

## Assumptions

- 網頁與 feed 完全重用「最近一次已推去 Discord」的榜單快照與新聞精選結果（由核心推播段持久化於
  `state/board.json`），不獨立重新選擇或改寫內容；發佈段只讀狀態、不做任何內容決策。
- 儀表板為「目前快照」單頁呈現，不提供逐日歷史封存或分頁瀏覽（與開發指南 §14.2 對「目前榜單」
  的描述一致）。
- repo 目前為 public 且預期維持公開；若實作當下 repo 已是 private，發佈階段將持續跳過，直到
  repo 改回 public 為止，不需要額外的人工遷移步驟。
- 發佈內容本身不涉及使用者帳號或存取控制——因為同一批內容已經透過 Discord 推播對外（伺服器
  成員可見），網頁只是換一個公開管道呈現相同內容。
